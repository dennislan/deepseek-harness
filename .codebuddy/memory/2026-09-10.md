# 2026-09-10

## native-macos 运行时自动更新（已实现并验证）

为 `native-macos` 的 `DeepSeekHarness.app` 增加启动时自动更新 **dsh 运行时**（不改 Swift 外壳、不改 `.app` 包）。

- 触发：启动后后台检查一次（独立 `Task`，等 dsh 就绪后再提示），无网络只记日志。
- 版本判定：GitHub `releases?per_page=1` 取 tag（**必须用列表接口，仓库所有 Release 都是 pre-release**）→ 去掉 `dsh-`/`v` 前缀 → npm registry 存在性校验 → 回退 `dist-tags.latest`。语义化比较含 pre-release 排序，无硬编码兜底、不降级。
- 落盘：`<DSH_HOME>/runtime/dsh-root`（默认 `~/.dsh/runtime/dsh-root`）。应用包内 `Contents/Resources/dsh-root` 只读作种子；解析时两者按版本取高者（相同取用户态）。
- 安装：内嵌 npm → `--prefix` 暂存 → `assemble-runtime.mjs` + `prune-node-modules.mjs` → 两个相对桥接符号链接 → `node bin.js --version` 预检 → 目录 rename 原子切换（保留 `dsh-root.previous`）→ `DshServer.restart()`；启动失败自动回滚并提示日志路径。
- 「关于」面板：`CommandGroup(replacing: .appInfo)` 自定义项，`applicationVersion` 取当前运行时版本。

### 顺带修复的潜伏缺陷（重要）
`build-release.sh` 原先 `embed_node_runtime`（阶段 2）在 `assemble_app_bundle`（阶段 4）之前，而后者开头 `rm -rf "$APP_DIR"` → **内嵌 Node 每次都被删掉**。已核实 2026-09-10 的 dmg 里 `Contents/Resources` 只有 `AppIcon.icns / Assets.car / dsh-root`，没有 node。现顺序改为 `compile_swift` → `assemble_app_bundle` → `embed_node_runtime`，并同时内嵌 npm（`lib/node_modules/npm` + `bin/npm`）。

## 体积问题分析（用户提出，方案未定，尚未实施）

- 用户反馈 `build-release.sh` 产出的包体积翻倍：dmg 42MB → 88MB，`.app` 146M → **278M**。
- 实测构成（拆开用户 22:05 的 dmg）：`dsh-root` 146M（**剪枝正常**，残留 `.d.ts`/`.map`/README 均为 0）+ `node/bin` 112M + `node/lib/node_modules/npm` 16M + 图标 0.1M。**增量 100% 来自本次新内嵌的 Node+npm**（压缩后 ≈46MB，正好等于 dmg 的增量）。
- 压缩方案实测：上游 `node-v24.12.0-darwin-arm64.tar.gz` 51.2MB；仅 `bin/node`+`LICENSE`+npm 重打包 41.3MB；单个 node 二进制 gzip -9 为 37.7MB。系统只保证有 `gzip`/`bzip2`（`xz`/`zstd` 只在 `/opt/homebrew`，不可依赖用户机器解压）。
- 关键结论：**归档在 dmg 内不可再压缩**，所以「内置压缩包」只能把 `.app` 降到 ~187M，dmg 仍 ~83MB；只有把工具链移出 bundle（复用系统 Node / 按需下载）才能让 dmg 回到 42MB。
- 已向用户提问三个选项（A 默认按需下载 + `--embed-node` 可选内置 / B 内置压缩包 / C 仅系统 Node），用户只回答了 npm 保留完整，主选项未答，随后转向新任务——**体积方案待用户确认后再动**。
